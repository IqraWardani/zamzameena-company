# PT Zamzameena Ainsa Synergy

Company profile PT Zamzameena Ainsa Synergy menggunakan Next.js App Router. Halaman Home, About, dan Contact menggunakan komponen Next.js. Halaman `/management/struktur` mengambil konten dari template HTML `struktur.html`.

## Menjalankan aplikasi Next.js

- Jalankan `npm install`, lalu `npm run dev`.
- Buka `http://localhost:3000`. Halaman tersedia di `/`, `/about`, `/business`, `/product-knowledge`, `/our-strength`, dan `/contact`.
- Project Next.js tetap menggunakan struktur App Router, sehingga dapat dibangun dengan `npm run build` dan dideploy ke Vercel.
- Konten halaman `/management/struktur` bersumber dari body `struktur.html` yang dirender di dalam layout Next.js.
- Gaya halaman berbasis template berada di `css/style.css`. Script browser aktif dimuat dari `public/js/main.js`.

## Mengganti foto dan logo

- Foto untuk halaman `/management/struktur` dapat disimpan sebagai `struktur.jpg` di `public/photos/`. Gunakan foto yang sesuai dengan deskripsi `alt` di template; bila gambar gagal dimuat, halaman menampilkan ilustrasi SVG cadangan.
- Logo untuk template tersedia di `public/assets/logo.png`; `public/assets/logo.svg` menjadi favicon dan fallback lokal.

## Setup Database

The contact form writes to `contact_submissions` only; it does not create participant profiles. Create a PostgreSQL database using Neon or Supabase, then set `DATABASE_URL` and `DIRECT_URL` in `.env.local`. `DATABASE_URL` is used by the running application through `pg.Pool`; for Vercel/serverless deployments, use the Supabase transaction pooler. `DIRECT_URL` is used by Prisma CLI commands, including client generation and migrations; use a direct or session-mode connection, not the transaction pooler. For local development, both variables may point to the same local PostgreSQL database. Use `.env.example` as a format reference; do not commit `.env.local` or any secret.

### Local PostgreSQL setup (safe, no migration run)

- Copy `.env.example` to `.env.local`.
- Set `DATABASE_URL` and `DIRECT_URL` only in your local environment. Both may use the same local PostgreSQL URL.
- Keep the value local to the machine; never commit or share the real connection string.
- `DIRECT_URL` is required when Prisma loads `prisma.config.ts`, including `prisma generate` during a build. There is intentionally no fallback to `DATABASE_URL`.
- Use the health endpoint to confirm the app is configured without exposing the URL or password: `npm run dev` then `curl -fsS http://localhost:3000/api/health`.
- Do not run Prisma migrations, resets, truncates, or destructive commands during initial setup. Approved additive migrations are documented below and must be applied only after a database backup.

### Admin access

- Admin sign-in is available only at `/admin/login`; no admin link is added to public navigation.
- Set a unique `ADMIN_SESSION_SECRET` in `.env.local` (at least 32 bytes). Generate it locally with `openssl rand -base64 32`; do not share or commit it.
- Provision an administrator only when explicitly intended by running `npm run admin:provision`. The command prompts for name, email, and a hidden password, stores a scrypt password hash, and creates the initial administrator role and permission catalog in a transaction. It does not run as part of build or startup and never prints the password.
- Admin sign-in uses Supabase Auth and then matches the authenticated email to an active `admin_users` account with an assigned database role before issuing the existing Admin session. Before enabling sign-in or password recovery, invite/provision each existing Admin email in Supabase Auth; existing scrypt hashes cannot be migrated to Supabase, so each account must establish a Supabase password. Configure `NEXT_PUBLIC_SUPABASE_URL` plus `NEXT_PUBLIC_SUPABASE_ANON_KEY`; the anon key is public and the Supabase secret/service-role key must remain server-only. Add `https://zamzameena.com/update-password` to Supabase Auth's allowed redirect URLs and set the Auth password policy to require at least 8 characters. Recovery updates Supabase credentials only and does not create Admin accounts or alter database roles.
- Admin session cookies are HTTP-only, strict same-site, limited to `/admin`, and expire after eight hours. Permissions and event assignments are reloaded from PostgreSQL for each protected request.
- The final database schema has no session table, so sessions are signed stateless cookies and cannot be revoked server-side before expiry. Rotate `ADMIN_SESSION_SECRET` to invalidate all sessions. The in-memory login throttler is best-effort per running process; production deployments with multiple instances should add a shared rate-limit provider before public exposure.
- Run the authorization policy tests with `npm run test:auth`.
- Event administration is under `/admin/events`. An administrator must have the relevant `events.*` or `ticket-types.manage` permission and an assignment to the specific event; the initial provisioning role grants these capabilities but does not assign other users to events. The event creator is assigned to their event automatically.
- Events follow the schema lifecycle: draft → published → closed/cancelled → archived where allowed. Ticket capacities cannot be set below existing registrations, and ticket sales windows and non-negative prices are validated on the server.
- Public registration is available at `/events/<event-slug>/register` only for published events during their registration window. Participant profiles are separate from contact submissions. The public flow returns only a registration number; it does not provide participant or registration lookup endpoints. Registration answers use the standard event-goals and accessibility/dietary questions and are snapshotted in `registration_answers`.
- Public registration tests run with `npm run test:registration`. A participant email is reused as the central profile key; one registration per event is enforced with transaction locks and the database unique constraint. Paid orders receive a server-generated invoice number derived from the event code and unique registration number; PostgreSQL enforces invoice-number uniqueness. No email verification is configured.
- Participant status and payment are available at `/participant` in the same browser used to register. The participant session is a signed HttpOnly, SameSite=Strict cookie with a 30-day expiry, scoped to only the registration issued in that browser session; it does not grant access to other registrations associated with the same unverified email. Set a separate `PARTICIPANT_SESSION_SECRET` (at least 32 bytes) in `.env.local`; generate it locally with `openssl rand -base64 32`.
- Payment claims use private S3-compatible object storage. Configure `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, and optionally `S3_ENDPOINT` in the runtime environment. Configure the bucket with public access blocked and do not grant public-read ACLs. The app uploads only JPEG, PNG, or PDF proof files up to 5 MB; `private_documents` stores metadata and an object key, never bytes or a public URL.
- Key Visual Management is available from the admin dashboard for assigned administrators with `events.update` permission. It accepts PNG/JPG/JPEG/WEBP up to 8 MB, verifies extension, MIME type, and image signature server-side, keeps replaced objects as history, and serves the active asset through a first-party route. New Key Visuals use a private Supabase Storage bucket configured with `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, and `SUPABASE_STORAGE_BUCKET`; the secret key is server-only and the bucket does not need public access. Existing S3 Key Visual object paths remain readable and deletable through the legacy S3 configuration; S3 settings are still required for payment proof documents. Apply `prisma/migrations/20261115_0002_event_key_visuals/migration.sql` (or its documented equivalent) after the base event schema before using the feature. This migration has not been applied automatically.
- `/api/private-documents/<id>/download` checks the participant session and ownership, or an admin's `payments.review` permission and event assignment, before creating a 60-second private download URL. Payment proof files are never written to `public/`.
- Paid registrations receive an invoice from the ticket price snapshot. The invoice number is shown in registration confirmation, the protected participant portal invoice preview/PDF, invoice email, and admin payment review. Rejected payment retries keep the existing invoice number. Invoice emails use the `notification_deliveries` outbox and Resend; configure `RESEND_API_KEY` and `RESEND_FROM_EMAIL` in the local/runtime environment. The registration still succeeds if email delivery is unavailable, and the participant can access the invoice from `/participant`. Payment submission is idempotent while a claim is pending review. Admin approval atomically marks payment approved, invoice paid, registration confirmed, issues one ticket, and records audit logs; the claimed amount must match the invoice amount exactly. Rejection requires a reason and allows a new payment claim; no payment is approved automatically. Zero-price registrations are immediately confirmed without an invoice or payment claim and receive one active complimentary ticket.
- Payment reviewers need the `payments.review` role permission and assignment to the relevant event. `npm run admin:provision` grants this permission to the initial `admin_operator` role when provisioning; an existing role can be updated explicitly with `npm run admin:enable-payment-review` (interactive confirmation required). Neither command creates an account automatically or assigns additional staff to events.
- Invitation operations are available at `/admin/invitations` to staff with `invitations.collect` permission and assignment to the selected event. Participant search is restricted to that event and returns only confirmed, ticketed, uncollected registrations. Staff can record collection by search or create a registration-bound code with optional expiry; code redemption checks event, target registration, active ticket, expiry, and one-collection uniqueness. Collection is audited and never creates a check-in. Grant the permission to the existing `admin_operator` role with `npm run admin:enable-invitation-collection` after reviewing its interactive confirmation; event assignments still limit access.
- Event check-in is available at `/admin/check-in` to assigned staff with `checkins.record`. Staff can validate a ticket code or search participants within the selected event; check-in requires an active ticket and confirmed registration, records the operator/time in the separate `check_ins` table, and writes an audit log. A registration can be checked in once. Check-in does not modify payment, invoice, invitation collection, or ticket state. Grant the permission to the existing `admin_operator` role with `npm run admin:enable-check-in` after reviewing its interactive confirmation.
- Public contact messages are stored only in `contact_submissions`; they are not linked to participant profiles. Administrators with `contacts.manage` can review submissions at `/admin/contacts` and update their status. The contact transaction adds a minimal `notification_deliveries` queue record containing only the submission ID; contact email delivery remains unconfigured, and no contact content is placed in notification payloads. Initial admin provisioning includes `contacts.manage`; grant it to every `admin_operator` member with `npm run admin:enable-contact-management` only after reviewing its interactive confirmation.
- Public participant registration records the required `event_registration_privacy` consent and policy version in `participant_consents`, uniquely per participant profile, consent type, and version. Contact-form consent is not written to participant consent records.
- Sales Management is available at `/admin/sales` for assigned events. `admin_operator` receives the separate `sales.read` and `sales.manage` permissions; the `marketing_director` role receives `sales.read` only, and the backend denies `sales.manage` to that role even if another role accidentally grants it. Provision a separate read-only director dashboard account with `npm run admin:provision-marketing-director`; the command prompts for account details and an event slug and creates no sales-member accounts.
- Sales members are event-scoped records (ARM, Kepala Cabang, Sales) and do not have dashboard logins. PostgreSQL enforces same-event reporting lines, the 5 ARM / 5 branch managers per ARM / 2 sales per branch active-member limits, unique member/referral codes, and immutable registration attribution except inside the audited admin correction action. Members with registrations, commissions, or direct reports are deactivated instead of physically deleted.
- Referral links use `/events/<event-slug>/register?ref=<CODE>`. The public form checks a code for the published event, but registration validates it again inside the database transaction and records both the seller ID and referral-code snapshot. Inactive members cannot receive new referrals. Historical invoice prices remain based on invoice snapshots; legacy invoices whose exact unit-price snapshot is unknown keep those fields NULL rather than inferring them from today's ticket price.
- Invoice snapshots include unit price, quantity, normal subtotal, discount, and amount due. Current registrations create one-ticket invoices with zero discount; `ticket_types.price_amount` remains the sole price source. Payment approval creates one idempotent 10% earned commission entry on the direct seller's normal subtotal in the same transaction that confirms payment and issues the ticket. Free registrations and orders with zero amount due do not earn commission. The ledger supports future adjustment entries; no refund workflow or commission-payout processing is implemented.
- Before applying production migrations, take and verify a database backup. Apply pending SQL migrations with `npm run prisma:migrate:deploy`; Prisma CLI uses `DIRECT_URL` from `.env.local` and does not reset or seed data. The sales module is introduced by `prisma/migrations/20261120_0004_sales_management_referrals_commissions/migration.sql`. Generate the Prisma client with `npm run prisma:generate` after the migration; this command also requires `DIRECT_URL`.
- `npm run test:contact` covers contact validation and separation, notification payload minimization, contacts permission checks, and private payment-proof access rules.

## Mengubah informasi

- Nomor dan pesan awal WhatsApp ada pada konstanta `WHATSAPP_NUMBER` dan `DEFAULT_WHATSAPP_MESSAGE` di awal `public/js/main.js` (format internasional tanpa tanda `+` atau spasi).
- Informasi kontak halaman Contact dikelola di `lib/contact-info.ts`.
- Bagan organisasi berada dalam array `ORGANIZATION` di awal `public/js/main.js`; ubah nama divisi atau daftar unit di sana.

- WhatsApp dapat dibuka dari sidebar dan bagian kontak. Tidak ada tombol WhatsApp mengambang.
